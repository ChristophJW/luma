# Luma — AR photo booth

Implementation plan for Snapchat-style AR face filters, native app only.

**Status: postponed.** Recorded 27 July 2026. Nothing here is scheduled and
nothing here is approved. This document exists so that when the question comes
back — and it will — the answer is a costed plan and a decision gate rather
than a fresh argument.

The feature itself was examined and deferred in `CHECKLIST.md`, *Considered and
deferred*. That entry stands. This is the plan that would be picked up **if**
the flip condition there ever fires.

---

## 1. What would have to be true before starting

From the deferral entry, unchanged:

- Hosts asking for it **unprompted** during validation (`CHECKLIST.md` §0), or
- a competitor visibly winning deals on it.

Two further preconditions, specific to how this repo is built today:

- **An iOS build path exists.** There is no `eas.json`, `/ios` is generated by
  prebuild and gitignored, and the Makefile has Android targets only. No AR SDK
  can even be *evaluated* on iOS until this is solved. Treat it as a
  prerequisite, not a phase-one task.
- **`CHECKLIST.md` §0 and §2 have passed.** Adding a licensed third-party SDK
  to an unvalidated product with unreviewed legal documents is the wrong order.

If any of these is false, stop reading and build the cheap alternatives in §9
instead.

---

## 2. The shape

**Not "Snapchat inside Luma" — a digital photo booth.**

Hosts already rent physical photo booths with prop boxes for roughly
€600–1200 a day. That framing is the whole reason this can exist here: it is a
thing that already happens at weddings, it is already paid for, and it survives
the *not Instagram* rule in `DESIGN.md` §3 in a way that dog ears do not.

Same technology, different curation. Paper crowns, a moustache on a stick,
garlands, confetti, a frame the couple's names sit in — with the event's film
treatment applied on top, so a booth photograph still belongs to the album.

It is sold as an **add-on**, enabled per event, and it is never the default.

### Three boundaries that do not move

1. **Never in `guest/`.** The guest camera is ~17 KB against a 30 KB budget
   enforced as a build failure by `scripts/check-bundle-size.mjs`. A face
   landmark runtime is roughly 200× that budget. Non-negotiable #3.
2. **Never in `host/src/CameraScreen.tsx`.** That screen is the disposable
   camera and the product's core mechanic. The booth is a separate screen with
   its own camera stack and its own entry point. Nothing is layered onto the
   roll.
3. **Per-event opt-in, server-controlled, remotely killable.** A crashing AR
   SDK during somebody's wedding is the worst failure this product can have.
   The app must be able to lose the feature mid-event without a store release.

## 3. Route: licensed SDK or build it

`expo-camera` has no frame-processor API, so either route means a second camera
stack inside the host app.

| | **A — Licensed SDK**<br>DeepAR · Banuba · Snap Camera Kit | **B — Build it**<br>vision-camera + ML Kit faces + Skia |
| --- | --- | --- |
| Quality | Occlusion, multiple faces, 3D, physics | 2D stickers on landmarks, visible jitter, one face in practice |
| Engineering | ~1 week integration | 2–4 weeks for a rough version |
| Binary size | +20–40 MB | +8–15 MB |
| Money | Licence fee, annually, plus a vendor DPA | None |
| Authoring | Vendor's creator tool; hire an artist | Hand-rolled, painful, and the bottleneck |

**Recommended: A.** Route B spends a month to arrive somewhere visibly worse
than what people already have on their phones, which is the one outcome that
makes the feature not worth having.

Do not pre-commit. Prices, terms and React Native support for all three vendors
change often enough that any figure written down here is stale by the time it
is read. Get quotes at the time.

---

## 4. Phase 0 — Spike and gate · 1 week

A real gate, not a formality. Two things could sink route A on this stack
specifically, and both are cheap to discover and expensive to discover late.

- [ ] Stand up the iOS build path (EAS, or local with a Mac). Prerequisite.
- [ ] Write the Expo config plugin for one candidate — maven repositories,
      Podfile entries, licence key placement. `/ios` and `/android` are
      regenerated by prebuild, so nothing can be hand-edited into them and
      survive.
- [ ] **New Architecture compatibility.** `app.json` sets
      `newArchEnabled: true` on RN 0.81, i.e. bridgeless. Several AR SDK React
      Native wrappers have lagged here. Verify on device, not in a changelog.
- [ ] Two candidates on real hardware, both platforms, **including a low-end
      Android** — `DESIGN.md` §7's phone from 2019 is the design constraint,
      not a flagship.
- [ ] Measure and write down: sustained FPS, thermal behaviour over a
      ten-minute session, battery drain, binary size delta, cold-start cost.
- [ ] Get written quotes, including the terms for a small launch volume.

**GATE.** If no SDK clears the device matrix, or the licence is
disproportionate to the add-on's price, fall back to route B *or* to §9 and
close this document again.

## 5. Phase 1 — Native integration behind a flag · 1.5–2 weeks

- [ ] `host/src/booth/BoothScreen.tsx` — SDK camera view, lens carousel,
      capture. `DESIGN.md` §7 applies here exactly as it does everywhere else:
      counter always visible, everything interactive in the bottom quarter,
      scrims mandatory, 44 pt targets, no text on live video.
- [ ] `host/src/booth/BoothScreen.web.tsx` — a stub that renders nothing. The
      host app also builds for `react-native-web` and the AR SDK will break
      that bundle otherwise. The repo already uses this pattern in
      `src/DateTimeField.web.tsx`.
- [ ] Capture writes a JPEG to disk, then hands off to the **existing**
      pipeline unchanged: `capture.reserve` → `putFile` → `capture.confirm`
      (`host/src/capture/api.ts`). Offline queueing, retry and recovery come
      free from `capture/queue.ts` and `capture/uploader.ts`. Do not fork them.
- [ ] Device capability check with a graceful absence: on an unsupported phone
      the booth entry point is **not shown**. Never shown, then broken.
- [ ] Two camera stacks now coexist. Verify permission handling, backgrounding,
      and interleaving booth and roll captures in one session.

## 6. Phase 2 — Product surface · 1.5 weeks

### Data model

- [ ] `Event.photo_booth_enabled` — boolean, default `False`.
- [ ] `Event.booth_shots_per_guest` — integer, default `0`, where 0 means off.
- [ ] `MediaAsset.capture_source` — `roll` | `booth`. Needed so the album can
      group booth photographs, so moderation and export know what they are
      handling, and so "a cohesive album rather than a random cloud folder"
      stays true rather than aspirational.

### Decisions, with recommendations

**Booth shots do not spend the finite roll.** The roll is the core mechanic
(non-negotiable #2). Muddling it for a novelty is the wrong trade. Give the
booth its own small allowance, capped separately.

**Booth configuration lives in event settings, not the wizard.** `DESIGN.md`
§11: a wizard step must ask only what cannot be sensibly defaulted, and this
defaults to off.

**Beauty and skin-smoothing filters are out of scope, permanently.** This will
be the first request after shipping. Write the answer down now, here, so it is
decided once: a filter that changes how a guest's face looks is a different
product and a different consent conversation.

### Plumbing

- [ ] Booth availability is read per event from the API on every session, so
      disabling it server-side takes effect without a store release.
- [ ] DE and EN strings in `host/src/i18n/`. Written in German first —
      `DESIGN.md` §12 — because German runs 30–40% longer and a lens carousel
      is a tight layout.

## 7. Phase 3 — The lens pack · 1–2 weeks, parallel, mostly external

Six to eight lenses, curated to the brand and built in the vendor's creator
tool. This is artist work, not engineering, and it is the part most likely to
be underestimated — a licensed SDK ships a renderer, not content. Budget for a
contractor.

- [ ] Every lens reviewed against the anti-brief (`DESIGN.md` §3). No neon, no
      sparkle, no gradient magic, nothing that reads as an AI feature.
- [ ] Every lens seen with the film treatments applied on top. A prop that
      fights `Silver` or `Safelight` is not finished.

---

## 8. Phase 4 — Compliance and release · 1 week, partly parallel

On-device landmark tracking that stores nothing and matches nobody is **not**
Art. 9 biometric data. It is the same distinction already written into
`api/apps/events/models.py` for blurring versus lookup: one hides a face, the
other identifies a person. That reasoning holds here — but it needs to be
written down rather than assumed.

- [ ] DPIA paragraph and a plain-language line in the privacy policy
      (`CHECKLIST.md` §2 is a GATE).
- [ ] The SDK vendor is a processor: DPA signed, and any licence-validation
      call home documented with its transfer basis. Non-negotiable #3 binds the
      *guest* capture screen and is untouched here — but a booth that quietly
      phones a vendor on launch still belongs in the records of processing.
- [ ] Google Play data safety form and App Store camera usage strings updated.
- [ ] Binary size increase reviewed as a download-conversion cost, not just a
      number. The host app is optional; every megabyte is a reason not to
      install it.
- [ ] `CHECKLIST.md` §11 device matrix extended with booth rows. That section
      is a GATE.

## 9. Build this instead, if the answer stays no

Unchanged from the deferral entry, and still the better trade until proven
otherwise — roughly 80% of the playfulness for about 1% of the cost:

- [ ] Frames and borders — white film border, event date, the couple's names, a
      venue stamp. Canvas only, no detection, near-zero bytes, and it
      *reinforces* the one-roll idea instead of fighting it.
- [ ] Draggable props positioned by finger — a moustache, a heart. No face
      detection at all; a few KB.
- [ ] The film treatments already specified (`Golden`, `Tungsten`, `Safelight`),
      which are not built yet and are the thing the product actually sells.

---

## 10. Cost, honestly

**Five to seven weeks** for one developer once Phase 0 clears, plus licence
fees and an artist for the lens pack. Phase 3 and most of Phase 4 run in
parallel with the engineering.

Risks, in the order they are likely to hurt:

1. **The lens pack is the hidden cost.** The SDK is a week; good content is not.
2. **Binary size** on an app that is already optional to install.
3. **Brand drift** — the feature arrives with its own gravity, and the requests
   that follow it point away from *warm, finite, unhurried*.
4. **Two camera stacks** to keep working across OS releases, permanently.

---

## 11. Kill criteria for this feature

Written in advance, because they are harder to admit later.

- No SDK sustains a usable frame rate on the low-end Android in the device
  matrix.
- Licence cost exceeds a sensible fraction of what the add-on can be priced at.
- The lens pack cannot be made to look like Luma rather than like Snapchat.
- It reaches a pilot wedding and hosts use it once, for novelty, and not again.
